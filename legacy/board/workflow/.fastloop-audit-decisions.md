# Fast-loop decision audit — GRAPE-SURPLUS bug

Auditor: fast-loop decision auditor · 2026-07-24 · scope: `tick.js` `pickFarmOrder` (~L314) +
`pickStoreOrder` (~L223), `config.json` farm/store strategy. Binding: DOCTRINE Rules 1, 4d, 5b, 6.

## Verdict (one line)

The pile is a **FARM production bug, not a store bug.** `pickFarmOrder` ranks GRAPES #1 on a
**paper** score (`profit × storeRate`) whose `storeRate` (81) is a fiction under the shared
single-lane store; grapes are `OVERSUPPLIED` (realizable ~20.7/h, `realizablePerHour_preWage`
$19/h). The farm defaults to that pick whenever it is not seeds-low and not mill-hungry, so it
grows a good the store rationally never buys. The store side is **correct as-is** and needs no
change. One minimal farm-side fix.

## Measured symptom (bot.log 2026-07-24)

```
00:24:46 SURPLUS grapes: 2158 units (limit 2000) ≈ $6906 frozen
00:30:34 SURPLUS grapes: 2198 units (limit 2000) ≈ $6924 frozen
00:30:34 FARM GRAPES shelf full (2198 in stock vs ~136/h over 24.0h) — growing beans instead
01:07:55 FARM GRAPES shelf full (2198 ...) — growing beans instead
01:20:06 STORE pick GRAPES x545 @ $6.49 profit=$287/h        <- store drains a little
```

Sawtooth: farm grows grapes → pile passes the 8h buffer → farm flips to beans → store sells one
grape batch → shelf has room again → farm flips **back to grapes**. Each grape unit freezes
~$3.20; ~2,200 units ≈ **$6.9k of cash frozen** in a good whose realizable retail is $19/h.

Realizable board (`board/.realizable.json`, fresh 01:37): apples/oranges/grapes **all
OVERSUPPLIED** (frac 0.13–0.14, realizable 20–28/h). Beans = **B2B-DEEP** (realizable 206/h, feeds
the Mill). Powder (coffee-ground) = **RETAIL-OK, realizablePerHour_preWage $1,272/h.** The chain
beans→powder is the money line; grapes are a dead lake.

## Root-cause trace — the exact condition

Farm crop is chosen at `tick.js` L762–767:

```js
let cropName;
if (seedStock < Math.max(2000, appleRate * Math.min(horizon, 4))) cropName = 'SEEDS';
else if (millHungry) cropName = 'COFFEE BEANS';
else cropName = pickFarmOrder(state).name;      // <-- returns GRAPES
```

`millHungry` (L746) = `(mill||millPlanned) && beanStock < powderRate*10*min(horizon,6)`.
With `powderRate = printedRates[119] = 18.04/h`, the hungry threshold is
`beanStock < 18.04*10*6 ≈ 1,082 beans`. The Mill consumes only ~180 beans/h, so once a bean batch
lands, `beanStock` sits **above 1,082 for hours** → `millHungry` is false → control falls to the
`else` → `pickFarmOrder` → **GRAPES**. That is the exact path that produces grapes into a clogged
lane.

### Why GRAPES specifically (pickFarmOrder scoring, L314–328)

`MODE=profit` ⇒ `score = profit × c.storeRate`, `profit = c.retailNet − matCost − farmWage/rate`:

| crop   | retailNet | matCost≈ | wage/rate≈ | profit≈ | storeRate | **score = profit×storeRate** |
|--------|-----------|----------|------------|---------|-----------|------------------------------|
| APPLES | 4.98      | 1.24     | 0.51       | 3.23    | 99        | 319 |
| ORANGES| 5.79      | 1.24     | 0.56       | 3.99    | 90        | 359 |
| GRAPES | 6.83      | 1.62     | 0.64       | 4.57    | **81**    | **370  ← winner** |

Grapes win by a hair: highest unit margin barely overcomes the lowest `storeRate`. **Both inputs
to the score are mirages under the current regime:**
- `storeRate` (99/90/81) is the "*this fruit owns the whole store lane*" rate, measured `store L1,
  accel x3` (config `_basis`). The store is now ONE shared lane contended by powder+steak+
  sausages+fruit; grapes' *realizable* retail rate is **20.7/h**, not 81.
- Ranking by realizable rate would flip the order to apples (27.8) > oranges (23.5) > grapes
  (20.7) — but it does not matter, because **all three carry verdict `OVERSUPPLIED`**, and
  DOCTRINE Rule 4d(2) says *never scale a MIRAGE/OVERSUPPLIED product*. The correct answer is
  "grow none of them beyond the store's tiny appetite; grow the feedstock the Mill turns into the
  $1,272/h powder line."

`tick.js` references `.realizable.json` **zero times**, so it cannot see that grapes are a lake.

### Why the existing guards don't stop it

`fruitBufferHours` cap (L774–795) does flip to beans — but only *after* the shelf physically
overflows, and its target uses `knowledge.sellRates[5].sellRate = 136.42/h` (fresh) — again the
grapes-own-the-lane rate, ~6.6× the realizable 20.7/h. So it lets grapes buffer to
`8h × 136 ≈ 1,088` before reacting, then the store drains one batch and the whole cycle repeats.
It is a reactive backstop on a mirage rate, not a fix.

## Store-side audit — priority is CORRECT, no change

`pickStoreOrder` (L223) runs exactly ONE order (single lane, MEASURED). It builds candidates that
have stock, applies the powder-burst gate, probes each with the game's own `Profit per hour`
(Rule 1 — ground truth), then sorts by `storePriority` tier (powder=1) then by $/h. That means it
**already picks the single best-$/h product for the one lane and never simultaneously "feeds the
losers"** — there is only one lane, and grapes only win it when nothing better is available
(powder below burst, steak sold out). Selling grapes at $287/h then is *better than idling the
lane* (Rule 6), so it is right. The store is not why grapes pile; it correctly refuses to sell
them when powder/steak beat them. **No store change. Do not add a realizable gate to the store —
the Rule-1 probe is the correct arbiter for the single live order.** (`.realizable.json` is a
*production* signal — what to make — not a per-order sell signal.)

## MINIMAL FIX — one function, one condition

Gate the farm's fruit default on the realizable verdict: when the fruit `pickFarmOrder` would grow
is `OVERSUPPLIED`/`MIRAGE` and a Mill can consume beans, grow **COFFEE BEANS** (feedstock →
powder, RETAIL-OK $1,272/h) instead of grapes. Degrades to current behaviour if the board file is
missing/stale. Keeps the farm busy (Rule 6), stops overproducing into the clogged lane (Rule 5b),
respects the verdict (Rule 4d(2)). It fires *before* the mirage-rate `fruitBufferHours` cap, so the
pile never forms.

**Add a helper** next to `knowledge()` (~L210):

```js
// Realizable verdict for a kind from board/.realizable.json (DOCTRINE Rule 4d). Returns null
// if the file is missing/unreadable so the caller falls back to its prior behaviour, never crashes.
function realizableVerdict(kind) {
  try {
    const r = JSON.parse(fs.readFileSync(path.join(DIR, 'board', '.realizable.json'), 'utf8'));
    return r.byKind?.[String(kind)]?.verdict || null;
  } catch { return null; }
}
```

**Change the crop default** at L767.

BEFORE:
```js
else cropName = pickFarmOrder(state).name;
```

AFTER:
```js
else {
  const fruit = pickFarmOrder(state);
  const v = realizableVerdict(fruit.kind);
  // DOCTRINE Rule 4d(2): never SCALE an OVERSUPPLIED/MIRAGE good. The single store lane can
  // absorb only ~20 grapes/h (realizable), so growing 495/h of them just freezes ~$3.20/unit.
  // Divert the farm's spare capacity to beans (B2B-DEEP, realizable 206/h) which the Mill turns
  // into powder (RETAIL-OK, $1,272/h). Only when a Mill exists/is planned; otherwise, and when
  // the verdict file is absent, keep the prior fruit pick (degrade gracefully, never idle — Rule 6).
  if ((mill || millPlanned) && (v === 'OVERSUPPLIED' || v === 'MIRAGE')) {
    log(`FARM ${fruit.name} verdict ${v} — not scaling into the shared store lane; growing beans (Mill feed)`);
    cropName = 'COFFEE BEANS';
  } else {
    cropName = fruit.name;
  }
}
```

### Before / after behaviour

| | before | after |
|---|---|---|
| crop when beans ≥1,082 & seeds ok | GRAPES (pile $3.20/unit, $19/h realizable) | COFFEE BEANS (Mill feed → $1,272/h powder) |
| grape pile | rebuilds to ~2,200 (~$6.9k frozen) every cycle | drains via store, never re-grown |
| farm idle? | no | no (beans) — Rule 6 held |
| `.realizable.json` missing/stale | n/a | falls back to GRAPES = today's behaviour, no crash |
| no Mill built | n/a | falls back to fruit pick (nothing else to grow) |
| store logic | unchanged | unchanged |

### Robustness / determinism

- No model call, no network, bounded O(1) file read wrapped in try/catch → **degrades to current
  behaviour** if the file is absent/corrupt (Rule: never crash the money loop).
- `mill`/`millPlanned`/`pickFarmOrder` are all already in scope at L767; `pickFarmOrder` result
  spreads `...c` so `.kind` is present. No new state, no new config key required.
- Bean orders remain water/seed/cash-throttled exactly as today (`inputBudget = 8% spendable`),
  so this cannot make the farm over-buy — it only changes *which* good the throttled output is.

## Out of scope (flag to strategist/board — NOT the fast loop's job)

1. **Beans can now accumulate** past the Mill's ~180/h appetite (farm bean rate 1,527/h printed,
   throttled by water budget). This is strictly cheaper than the grape pile ($0.56 vs $3.20/unit)
   and has a sellable downstream (powder), so it is the least-bad busy-work — but if it piles, the
   board should add a `surplusWatch` entry for beans (118) and decide the real pivot (2nd Mill,
   pause farm, or drop grapes/oranges from `farmProducts`). The fast loop must not decide company
   direction.
2. **`fruitBufferHours` cap uses `knowledge.sellRates[5]=136/h`** (grapes-own-the-lane) — ~6.6× the
   realizable 20.7/h, so the buffer target is ~6× too big. The primary fix short-circuits it (crop
   becomes BEANS before that block runs), so no change is *needed*; but if the board ever wants
   fruit buffered on the shelf, size it to the realizable rate, not the learned lane rate.
3. **`farmProducts[].storeRate` (99/90/81)** are stale `store L1, accel x3` snapshots. Consider
   the strategist re-deriving them from realizable rates so the paper score stops disagreeing with
   the board — but that is a strategy-data edit, not a fast-loop engine change.

## Recommendation

Apply the single fix above (helper + L767 condition). It is the minimal change that stops the
measured grape pile, honours Rule 4d(2), keeps the farm busy (Rule 6), and cannot destabilise the
loop. No store change. No config change required to ship it.
