# Fast-loop robustness audit — tick.js (2026-07-24)

Scope: real defects/fragilities in `tick.js` **other than** the grape-crop / realizable-metric
issues already on the board. Each item cites the line, a concrete trigger, and a minimal diff.
All findings verified against the live `bot.log`, `config.json`, `run-tick.sh`, and the page
scripts. Guardrails respected: no strategy pivots, deterministic-only, degrade-gracefully.

Ranked most-severe first.

---

## 1. [HIGH] Stuck detector never fires for a persistent single-building stall — its window is smaller than 2 ticks

**Lines 885 / 895 / 914** (stuck detector).

```js
const recent = fs.readFileSync(LOG, 'utf8').trim().split('\n').slice(-40);   // 885
...
if (worst && worst[1] >= 4) { ... escalate/spawn strategist ... }            // 895
else if (worst && worst[1] < 2 && fs.existsSync(flag)) { unlink; }           // 914
```

**Measured:** a tick now emits **~22 log lines** (verified from the last four `STATE money=`
markers in bot.log: gaps of 21, 22, 23 lines — 4 real buildings each log a `BUSY`/pick line,
plus COLLECT/CHAT/PRICE/SURPLUS/STATE/NEXT DUE/LEARN). So `slice(-40)` ≈ **1.8 ticks** of
history.

**Failure scenario:** the exact case this detector exists for — one building stuck producing
the same failure every tick (the "7-hour water stall", "repeated BUY-MISSING refusal", a
`SESSION lost` loop) — logs **one** matching `failSig` line per tick. In a 40-line (≈1.8-tick)
window that signature appears at most ~2 times, so `worst[1]` never reaches the `>= 4`
threshold. **The strategist is never woken; the loop grinds the failure forever** — precisely
the "escalate, don't grind" guarantee (Rule 5, DOCTRINE §5.4) that this block was written to
provide. To hit 4 occurrences you now need 4 failures inside ~1.8 ticks, i.e. **4 buildings
failing simultaneously in one tick**, which inverts the intent from "persistent" to
"simultaneous".

**Minimal fix (one line):** size the window to cover several ticks, not several lines. At
~22 lines/tick, 4 ticks ≈ 88 lines; use a margin:

```js
const recent = fs.readFileSync(LOG, 'utf8').trim().split('\n').slice(-160);   // ~7 ticks
```

With `-160` a once-per-tick failure reaches `worst[1] >= 4` after ~4 ticks (~8–48 min depending
on cadence) and still ages out below the `< 2` clear threshold ~7 ticks after recovery. No other
change needed; the threshold constants stay as-is. (A more correct version segments `recent` on
`STATE money=` markers and counts *distinct ticks* a signature appears in, but the window widen
is the minimal, deterministic, safe diff.)

**Note:** this is load-bearing for every other fragility below — the stuck detector is the
backstop that is supposed to catch them. It is currently blind.

## 2. [MED] `recentEarnRate(buildingId)` ignores its argument — every building's upgrade payback is priced off the STORE's sell rate

**Lines 198–207** (definition), used at **line 491** (`upgradeWorthIt`) and **line 697** (farm horizon).

```js
function recentEarnRate(buildingId) {          // 198  — buildingId is NEVER referenced again
  const rows = ...observations.jsonl...
    .filter(o => (o.type==='sell'||o.type==='produce') && o.ok && o.perHour>0);
  ... return average of last 5 .perHour ...
}
```

**Verified:** the `buildingId` parameter appears only in the signature; the body reads a global
list. Moreover only **`type:'sell'`** observations carry `perHour` (line 591). The three
`type:'produce'` observations (lines 614, 678, 851) have **no** `perHour`, so `o.perHour>0`
filters them all out. Net effect: `recentEarnRate(anything)` returns the **store's recent sell
$/h**, regardless of the building id passed.

**Failure scenario:** `upgradeWorthIt(b, up)` (line 491) sets `earning = recentEarnRate(b.id)`
and `gain = earning`, then `payback = up.assumedCost / gain`. For a Mill / Slaughterhouse /
Farm upgrade this prices the payback off the **store's** sell rate, not the building being
upgraded. A powder-burst window (store $/h spikes to ~$1,300) would wrongly *approve* a Mill
upgrade; a fruit-only window (~$290/h) would wrongly *reject* one — in both cases the decision
is disconnected from the building's own economics. Dormant today (all `upgrades[*].enabled`
are `false`), but the **standing plan explicitly queues** Farm L2, Mill L2, Bakery/Oil-rig L2
upgrades (config `buildPlan._after`), so enabling any of them trips this immediately.

**Minimal fix:** make the function actually per-building. Either tag sell/produce observations
with the building id and filter on it, or (smaller) rename to make the contract honest and give
`upgradeWorthIt` a real per-building number. Smallest correct diff — filter observations by the
building's own product kinds:

```js
function recentEarnRate(buildingId) {
  // map buildingId -> the kinds it sells/produces, filter rows to those kinds, else global.
  ...
}
```

At minimum, until per-building data exists, the `upgradeWorthIt` "no earnings history → allow"
branch (line 492) should be the path for non-store buildings rather than trusting a store-derived
rate. The farm-block call at line 697 happens to want the store rate, so it is accidentally
correct — but that only masks the bug.

## 3. [MED] `price-history.jsonl` grows unbounded and is fully read + parsed every tick

**Lines 401–402** (append then full read); **run-tick.sh line 46** (rotation set).

```js
fs.appendFileSync(histFile, JSON.stringify({ t, p: snap }) + '\n');            // 401
const lines = fs.readFileSync(histFile, 'utf8').trim().split('\n')
                .slice(-((CFG.priceAlert||{}).windowSamples || 36));           // 402
```

**Verified:** run-tick.sh rotates only `$LOG` and `observations.jsonl` at 5 MB
(`for f in "$LOG" .../observations.jsonl`). `price-history.jsonl` is **not** in that set, yet
it is appended **every tick** and then **read in full** on line 402 only to keep the last 36
samples. Current size 95 KB / 662 lines after ~2 days.

**Failure scenario:** DOCTRINE §5 commits this bot to running "unattended for weeks". At
~330 samples/day the file reaches multiple MB over a month and never stops; every 2-minute tick
pays an O(file) read + `split` + `JSON.parse`-per-kept-line that scales with total history, not
with the 36-sample window it needs. Same O(file) pattern exists at line 112 (`pa-offers.jsonl`,
read whole to get the last line) but that file is appended only a few times a day, so
`price-history.jsonl` is the one that actually bites.

**Minimal fix:** cap the file after appending (bounded, deterministic, no new rotation policy):

```js
fs.appendFileSync(histFile, JSON.stringify({ t, p: snap }) + '\n');
let lines = fs.readFileSync(histFile, 'utf8').trim().split('\n');
const keep = (CFG.priceAlert||{}).windowSamples || 36;
if (lines.length > keep * 4) {                       // occasional compaction
  lines = lines.slice(-keep * 4);
  fs.writeFileSync(histFile, lines.join('\n') + '\n');
}
lines = lines.slice(-keep);
```

Or simply add `price-history.jsonl` to the run-tick.sh rotation list. Either bounds both the
file and the per-tick read.

## 4. [LOW] `next-due.txt` is computed from the *pre-order* busy snapshot, defeating the cheap early-out for one cycle after every placement

**Lines 868–875**, using `b.busy` from the `state` captured at **line 385**.

```js
const dueTimes = managed.map(b => b.busy
  ? new Date(b.busy.started).getTime() + b.busy.duration*1000
  : Date.now());                                   // 872-873
const nextDue = new Date(dueTimes.length ? Math.min(...dueTimes) : Date.now());
```

**Failure scenario:** the building loop (571–861) places new orders but never refreshes
`state.buildings`. A building we *just* started still shows `b.busy === null` in the snapshot,
so its `dueTime` is `Date.now()` and `nextDue` collapses to ~now. run-tick.sh then sees
`wait = due-now ≈ 0` (not `> 45`), skips its cheap early-out, and runs a **full CDP tick 2
minutes later** instead of sleeping until the real completion. The next tick reads fresh busy
state and self-corrects, so the cost is bounded to one extra full browser tick per
order-placement round. (Benign when a managed building is legitimately idle — e.g. the Mill
"waiting for beans" — since `now` is then the correct answer; it only over-reports when all
managed buildings go busy in the same tick.)

**Minimal fix:** after placing an order, record the intended completion locally and prefer it
over the stale snapshot, e.g. keep a `startedAt[b.id] = Date.now() + estHours*3600e3` when an
order succeeds and fold it into `dueTimes`. Low priority — waste is small and self-healing —
but it is a real correctness gap in the very optimization the block exists for.

## 5. [LOW / LATENT] `config.json` lost-update race — tick serializes a start-of-run in-memory copy

**Line 19** (read once at start) vs **lines 470 and 545** (write the whole `CFG` object back).

```js
const CFG = JSON.parse(fs.readFileSync('config.json'));      // 19
...
CFG.accelerationFactor = state.accel.multiplier;             // 469
fs.writeFileSync('config.json', JSON.stringify(CFG, null, 2));  // 470  (also 545 on build success)
```

**Failure scenario:** `run-strategist.sh` wraps only its *browser* commands in
`flock .tick.lock`; its direct file edits to `config.json` are not under that lock. If a
strategist rewrites `config.json` while a tick holds the lock, and the tick then hits an accel
regime change (470) or a build success (545), the tick writes its **stale start-of-run CFG**,
silently discarding the strategist's edit. Currently near-inert (acceleration has been a stable
×1 since 2026-07-22 and `buildPlan.enabled=false`, so neither writer fires), which is why it has
not bitten — but it is a genuine read-modify-write-whole-file race that will matter the moment
acceleration returns or the fast loop is re-armed to build.

**Minimal fix:** on the rare write paths, re-read `config.json` immediately before writing and
patch only the single field (`accelerationFactor`, or the `buildPlan` keys), rather than
serializing the whole start-of-run object. Keeps the deterministic behaviour while making the
write a targeted merge instead of a full clobber.

## Checked and found OK (no defect)

- **Slot counting (lines 528–529).** `slotUsers` filter (`!freeAndLocked && category!=='seasonal'`)
  correctly excludes the Beach market; `freeSlots = maxBuildings - realBuildings` matches the
  measured "2 free slots" at Lv.10. No off-by-one.
- **String/number key access** for `surplusWatch`, `storePriority`, `printedRates`, `stock`,
  `price`, `mods` — JS coerces numeric object keys to strings, so `stock["5"]` == `stock[5]`; all
  accesses resolve.
- **Surplus watch (438–457)** correctly writes/clears its flag and throttles wakes; it never
  sells by design.
- **`printedRates` staleness** (powder 119 baked with the −23% nerf) is documented and fails in
  the *safe* (under-order) direction; not a defect.
- **`produce.js` ignoring `minCashAfter`/`maxBuyCost`** is by design (it never buys); inputs are
  pre-bought and orders sized to on-hand stock, so no input is consumed on a failed PRODUCE.
- **Farm/Slaughterhouse cash floors** (`farmInputFloor`, `factoryInputFloor`) self-heal via store
  inflow; the only way they strand a building is if the store itself cannot sell — which is the
  known realizable-metric / single-lane issue already on the board, not a new defect.
