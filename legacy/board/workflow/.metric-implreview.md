# Implementation-risk review — `realizable.js` spec (`.metric-spec.md` §9/§10) vs live code & data

Reviewer pass on 2026-07-24. Method: extracted the §9 module verbatim, ran it against live
`game-facts.json` (gen 2026-07-23T02:06) + `board-data.json` (gen 2026-07-24T03:25Z), traced the
recipe graph, and diffed §10's wiring against the *actual* `industry-report.js` variable names.

**Bottom line:** the §9 code runs clean and reproduces §7 to 3 digits (crude 200.4, dough 13 892,
samosa rr 5.66 / $3 303, flight-comp 0.057 → MIRAGE $0, steak $126, apples OVERSUPPLIED $5,
carbon-fiber B2B-DEEP 160). No NaN/Infinity. Graph is **acyclic** (0 cycles, 0 self-loops),
converges in **9 iters**, maxDelta 0. So the design is implementable as written. The risks below are
robustness/wiring hazards, not "it doesn't run today" blockers.

---

## (a) Reliance on unreliable fields

**R1 — MODERATE — the `unitsSoldAnHour==1` placeholder leaks back in for any *live-lake* aircraft.**
The dead-lake gate (`retailClears`) only defends *dead* lakes. Right now **quadcopter (k98) has a LIVE
retail lake** (`averagePrice = 1344.9`, sat 0.72), so the leaf takes
`retailTerm = max(unitsSoldAnHour=1, consumption=0.478) = 1` — the exact "never trust bare 1" the spec
§2 forbids. It is *contained today* (aircraft are terminal; quadcopter's inputs are {19,21,22,47}
electronics, none an aerospace part, so aerospace parts 80–89 still zero out correctly), but it is a
latent hole: the sentinel 1 flows into k47/k19/… derived demand, and any future aircraft lake going
live widens it.
*Fix:* treat `unitsSoldAnHour===1` as a sentinel before the `max`: `us = (usRaw===1 ? 0 : usRaw)`,
or gate on a known placeholder set (aircraft/high-value low-rate), so a live aircraft lake still seeds
only `consumption`.

**R2 — OK (the proven failure is correctly avoided) — but the reliability surface moved.**
The proven-dead fields (`consumption=0`, `unitsSoldAnHour=0` for real B2B) are correctly **not** relied
on for B2B goods — crude/dough/carbon get demand purely from downstream propagation and stay alive.
Good. The catch: the entire tree's *magnitude* now rests on `amountSoldRestaurant` (realm-wide
restaurant aggregates) and the `averagePrice` clears-gate, and the leaf samples the **single most
recent day** (`retailData[n-1].amountSoldRestaurant`) with **no smoothing/cap**. That is why apples
`derived = 1.6M` — it is `8 ×` apple-cider's single-day cider-restaurant figure (4 774 653/day ⇒
198 944/h). One spike in one day's restaurant number swings a whole subtree by millions.
*Fix:* use a median/mean of the last min(7,n) days for `restaurant(k)`, and winsorize obvious outliers.

**R2b — NOTE — the "samosa is THE volume king" narrative (§0/§7) is not the whole picture.**
Samosa's restaurant off-take (15 689/h) is only **7th**; milk 461 858/h, orange-juice 217 868/h,
apple-cider 198 944/h, coffee-ground 120 877/h, ginger-beer 68 841/h, butter 27 643/h, cheese
16 652/h all exceed it and none are seasonal. Samosa is special only because its retail lake is *dead*
(`avgPrice=0`) so it needs the restaurant-driven B2B-DEEP rescue; the others clear retail and are
handled in the retail branch. The classification is fine, but do not present samosa as the single
largest sink — it is the largest *dead-lake* sink.

**R2c — NOTE — seasonal goods still inject demand into the graph.**
`icecream-apple (k154)` is `retailSeason=Summer`; SEASONAL only changes k154's *own* verdict, it does
**not** remove k154's leaf from propagation, so its inputs still inherit its (in-season) pull. Usually
correct (real demand is real), but be aware off-season goods can still inflate a parent's `derived`.

## (b) Graceful degradation when `orderBooks` is empty

**Status:** on disk `orderBooks` is **not** empty — 7 self-traded kinds (2,3,4,5,66,111,119) have full
depth. But the code degrades correctly when a book is absent:
`(board.coo&&board.coo.orderBooks)||(board.cmo&&…)||{}` then per-kind stale fallback
(`pk = isUp?0.6:0.5, bookStale=true`). Verified: crude/dough/carbon already run the stale path and
still classify correctly. **So (b) is genuinely handled for orderBooks.**

**R3 — MODERATE — the real unguarded crash is `board.market`, not `orderBooks`.**
Lines ~250/254 do `for (const t of board.market.ticker)` / `board.market.retail` with no guard. A
missing/empty `board.market` → TypeError. Because §10 wires `buildRealizable()` with **no args** (it
reads `DIR/board-data.json`, ignoring the capture passed to `industry-report`), a stale/missing/corrupt
`board-data.json` now makes the previously-working `node industry-report.js defs.json capture.json`
crash outright — a regression for the strategist's building-ranking loop.
*Fix:* guard `board.market?.ticker || []` / `?.retail || []` inside `realizable.js`, and wrap the
`buildRealizable()` call in `industry-report.js` in try/catch that falls back to the paper `rate`.

**R4 — MINOR — silent empties.** Empty ticker ⇒ all `perUnitProfit` null ⇒ empty ranked table with no
message. Empty retail ⇒ everything routes through the B2B branch on a consumption-only leaf (degraded
but not wrong). Acceptable; emit a one-line warning when ticker/retail is empty.

## (c) Recipe-graph termination & leaf handling

**R5 — OK.** No infinite recursion is possible: both `realizable.js` and the existing
`derived-demand.js` use **bounded fixed-point iteration** (500 / 1000 caps, early break at 1e-12 /
1e-9), not recursion. Live graph is **acyclic** (verified: 0 cycles, 0 self-referential recipes),
converges in 9 iters, no non-finite values. Leaf retail goods are handled correctly — a good nothing
consumes has `consumers[k]` undefined ⇒ `A(k)=L(k)`.

**R6 — LATENT — no cycle guard, no non-convergence signal in `realizable.js`.**
If a future data/recipe change (or a bad scrape) introduces a cycle with gain ≥ 1, the module silently
runs the full 500 iters and returns huge/`Infinity` numbers with **no warning**, feeding a garbage
ranking to the board. Base commodities already reach `A ≈ 15.7M` (water) legitimately via DAG fan-out,
so a gain≥1 cycle would blow up fast and invisibly. `derived-demand.js` *already* has a topo cycle
detector + iters/maxDelta report — **port it in**: detect cycles (assert acyclic or warn) and attach a
`{converged:bool, iters, maxDelta}` to the output so downstream can distrust a non-converged run.

## (d) Wiring into `industry-report.js` (checked against actual variable names)

Confirmed present and correctly named: loop `kind = Number(kindStr)`, `rate`, `netSell`, `inputCost`,
`b.wage`, `name[kind]` (dict), `rows`, `skipped`, `by`. `require('./realizable')` resolves (same dir).
`RZ[kind]` with a numeric key coerces to the string keys `byKind` uses; `game-facts.json` and
`defs.json` cover the **identical 151 kinds**, so no lookup gaps. The `$` formula reuses
`industry-report`'s own `(netSell-inputCost)*realizableRate - b.wage`, so the price-basis mismatch
below does **not** corrupt the dollars — only the rate/verdict. Remaining issues:

**R7 — MODERATE — data-source divergence defeats the "FRESH capture" re-rank.**
`industry-report.js` is invoked `node industry-report.js defs.json <FRESH-capture>.json`
(run-strategist.sh:57, STRATEGIST.md:57) and ranks paper $/h off that fresh capture's prices. But
`buildRealizable()` ignores argv and reads `DIR/board-data.json` (last gen 03:25Z — can be hours
stale). So `realizableRate`/`verdict` come from a *different, possibly stale* snapshot than the capture
the strategist deliberately grabbed.
*Fix:* thread the capture/prices into `buildRealizable({boardPath})` or a `pricesOverride`, or have
`industry-report` pass its own ticker; at minimum, refresh `board-data.json` immediately before the
re-rank and note the dependency.

**R8 — MINOR — §10 step 3's `paybackH` snippet doesn't map to the real code.**
`paybackH = Math.round(b.cost / Math.max(1, realizablePerHour))` is written as if `b` and
`realizablePerHour` are in scope at sort time — they aren't; in the sort callback `b` is a **row** and
`paybackH` is a per-row property set at push (line 95). Recompute `paybackH` **inside the row loop**
from `realizablePerHour`, keeping the `Math.max(1, …)` guard (realizable $/h can go ≤0 after the
haircut ⇒ otherwise negative payback).

**R9 — MINOR — filter basis.** Line 82 `if (profitPerHour <= 0) continue;` still filters on **paper**
profit. Decide whether the cut should be on realizable $/h; today a good with positive paper but ≤0
realizable is still ranked (with negative realizable $/h).

**R10 — MINOR — internal contradiction in §10.** Step 2 says `if verdict.startsWith('MIRAGE') continue`
(drop the row); step 4 says keep the paper $/h "so the board sees aerospace $3 849 → $0". You can't
show the haircut for rows you `continue` past. Pick one — keep MIRAGE rows with `realizablePerHour=0`
so the haircut column is visible.

**R11 — NOTE — the `.realizable.json` artifact is only written by the CLI.**
`board/.realizable.json` (consumed per §11 by the strategist and `board/board-workflow.js`) is written
only under `require.main === module`. Merely `require`-ing the module from `industry-report.js` never
writes it, so a cron/refresh must actually run `node realizable.js` for those consumers to see fresh
data. Also `realizable.js` does not yet exist as a file — it lives only in spec §9 (which I verified
runs verbatim), so implementation = drop §9 to `sim/realizable.js` unchanged.
