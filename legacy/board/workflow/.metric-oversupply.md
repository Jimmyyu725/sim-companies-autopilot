# Metric spec: oversupply & elasticity discount (`realizableRate`)

Status: DESIGN, verified against live data 2026-07-24 (board-data.json generated 07-23T22:25,
market-snapshots.jsonl, knowledge.json). This is the correction layer for the paper-$/h bug in
`industry-report.js`. `realizable.js` should implement it.

## 0. The bug this fixes

`industry-report.js` computes `profitPerHour = (netSell - inputCost) * rate - wage` with
`rate = producedPerHourRaw * 0.8087` — i.e. it assumes **every unit a building makes sells at
the current price**. That is false for two reasons:

1. **The market only absorbs so much** (aerospace: paper $2,600-3,849/bldg-hr, realm demand ~0.057/h).
2. **Our own added supply presses the price down** (fruit already at saturation ~1.5; adding output
   pushes it toward the dead point).

The fix is a unit-rate haircut: `realizableRate` = the units/hour we can actually sell **near the
current price**, so downstream $/h uses `(netSell - inputCost) * realizableRate - wage`.

## 1. Verified market physics

### 1.1 The demand curve (exact, verified)

For every retail product, the game's own feed satisfies, to 4 decimals across all 80 products and
the 28-day `retailData` history:

```
demand  =  clamp(1 - S/2, 0, 1)          # S = saturation
```

Checked: apples S=1.4770 → demand 0.26152 (feed: 0.26152); steak S=1.4385 → 0.28074 (feed 0.28074);
samosa S=0.10 → 0.95 (feed 0.95). `demand` is therefore **not** independent information — it is the
price/sell-through multiplier `m(S)` and saturation is the single retail oversupply state variable:

| S     | m = 1-S/2 | meaning                                    |
|-------|-----------|--------------------------------------------|
| 0.0   | 1.00      | empty lake, full price + full velocity     |
| 1.0   | 0.50      | at the demand line                         |
| 1.5   | 0.25      | oversupplied (fruit lives here)            |
| 2.0   | 0.00      | **dead** — price floored, nothing clears   |

**Dead-lake tell (verified):** aircraft k94-99 sit at S≈1.2-1.3 but their `averagePrice` is `null`
— the market is not clearing at all, so their nominal `unitsSoldAnHour` (=1) is never realized.
Cars k53-57 at S≈0.53-0.74 carry real prices ($2,828-8,409) and `is_up=true`. **`averagePrice == null`
(or 0) while listed = a dead retail lake**, regardless of the saturation number.

### 1.2 There are two lakes, read differently

- **Retail lake** — depth = `saturation` (board-data `market.retail[].saturation`; series in
  `retailData[]`). Applies to goods with a retail/restaurant sink.
- **Exchange lake (B2B)** — depth = **sell-book days-of-supply**. Applies to intermediates with no
  retail sink (crude, dough, cockpit, rocket-engine). `saturation` does not exist for them.

### 1.3 Three demand channels (this is what defeats the crude-vs-aerospace trap)

`consumption` and `unitsSoldAnHour` are **both 0** for crude(10), dough(137), samosa(143) **and** for
every aerospace intermediate — so neither field, alone or together, can separate real from dead
(stated as CRITICAL FAILURE in the brief; confirmed). The separator is the **recipe graph**. Total
absorption of a kind:

```
A(k) = retailSink(k) + restaurantSink(k) + derivedDemand(k)
```

- **retailSink** = `unitsSoldAnHour` (units/h) — apples 110, steak 35, planks 120; 0 for B2B goods.
- **restaurantSink** = `retailData[-1].amountSoldRestaurant / 24` (units/h). **This field is why
  samosa is the volume king and is invisible to `unitsSoldAnHour`:** samosa restaurant sales =
  376,539/day = **15,689/h**, rising 335k→376k over 28 days, at S pinned to 0.10. Apples/steak = 0 here.
- **derivedDemand** = recursive B2B demand from the recipe tree (§1.4).

### 1.4 Recursive derived demand — realized, not nominal

Build the consumer graph from `recipe`: if C's recipe lists `q` units of `k`, then C consumes
`q * production(C)` of `k`. At steady state `production(C) ≈ A(C)`, giving a fixed point solved by
iteration over the DAG:

```
derivedDemand(k) = Σ_over_consumers_C  recipe_C[k] * A(C)
```

**Critical refinement — seed the terminals with *realized*, not nominal, demand.** A terminal's
direct demand is credited **only if its lake actually clears**:

```
realizedDirect(k) = restaurantSink(k)
                  + ( unitsSoldAnHour(k) * m(S)   if retail avgPrice is non-null and > 0
                      0                            if avgPrice is null/0  (dead lake)
                      unitsSoldAnHour(k)           if pure-exchange, no retail entry )
```

Propagated up the tree this is the honest kill: aircraft carry `avgPrice=null` → seed 0 → the whole
aerospace subtree (cockpit, attitude-control, rocket-engine, jet-engine, carbon-fiber) inherits ~0.
Crude/dough reach terminals that **do** clear (fuel→cars with `is_up=true` real prices; dough→samosa
at 376k/day) so they keep large derived demand. Measured:

| kind                | recursive A (realized) | verdict  |
|---------------------|------------------------|----------|
| samosa (restaurant) | 15,689 /h              | REAL     |
| dough (137)         | 13,873 /h              | REAL     |
| crude oil (10)      | 104 /h                 | REAL     |
| carbon-fiber (75)   | 0.0 /h                 | MIRAGE   |
| cockpit (81)        | 0.0 /h                 | MIRAGE   |
| attitude-ctrl (82)  | 0.0 /h                 | MIRAGE   |
| rocket-engine (86)  | 0.0 /h                 | MIRAGE   |
| combustion-eng (52) | 6.5 /h                 | MIRAGE   |
| jet-engine (89)     | 0.0 /h                 | MIRAGE   |

Even the cruder **nominal** seeding (before the realized refinement) already separates them by
100-680× (crude 4,099 vs aerospace 6-41), so the classification is robust to seeding choice; the
realized refinement just widens the gap to a clean 0. **Never let derivedDemand credit flow through a
non-clearing terminal.**

> Caveat, stated honestly: `A` in *units/h* under-reads high-value/low-volume goods (cars legitimately
> sell ~1-2 units/h). Use `A` as a real/dead **classifier** and as the retail headroom base (§3), not
> as a dollar ranking — dollars come later from `realizableRate * price`.

## 2. Oversupply detection

### 2.1 Retail goods — level + trend + clearing

From `board-data market.retail[k]` and its `retailData[]` (28 daily points):

- **level**: `S = saturation`.
- **trend**: `dS = ` slope of `saturation` over the last min(7, n) `retailData` days, per day
  (or across `market-snapshots.jsonl` timestamps when board-data is stale). Sign is decisive:
  - `dS < 0` while `S>1` → **DRAINING**: current supply < absorption, price recovering → real room to add.
  - `dS ≈ 0` while `S>1` → **OVERSUPPLIED** steady loop: you can only take churn; adding presses price.
  - `dS > 0` while `S>1` → **FLOODING**: getting worse; headroom → 0.
- **clearing**: `avgPrice == null || 0` → **DEAD-LAKE** (§1.1), `realizableRate = 0`.

Live readings: apples S=1.494, dS=+0.0002/day → OVERSUPPLIED (flat, no room). steak S=1.343,
dS=-0.009/day → DRAINING (price rose $54.9→$57.5 over the window). planks S=1.097, dS=-0.0035 →
DRAINING. samosa S=0.10 → OPEN.

### 2.2 Exchange / B2B goods — days-of-supply from the sell book

`board-data.orderBooks[k]` is the SELL-side listing depth = **supply already sitting in the lake**
(deep = oversupplied, NOT demand — noted in brief). Days-of-supply:

```
bookDepth(k) = Σ quantity of SELL listings within (1+p_band) of best ask     # p_band ≈ 0.05
DoS(k)       = bookDepth(k) / A(k) / 24                                        # days
priceKeepExch(k) = clamp(1 - DoS(k)/DoS_dead, 0, 1)                            # DoS_dead ≈ 30 days
```

Deep book relative to derived demand = a durable oversupplied exchange lake → low `priceKeepExch`.

**Fallback (this cycle `orderBooks` is empty — brief warned board-data may be stale):** when the book
is absent, do **not** guess depth. Instead:
1. the real/dead call is already made by `A(k)` (§1.4) — aerospace dies on `A≈0` without needing the book;
2. for survivors, set `priceKeepExch = 0.6 if ticker.is_up else 0.5` (a neutral, deliberately
   conservative hold), and optionally refine with the slope of `price-history.jsonl` for that kind.
   Mark the row `bookStale:true` so the board knows the exchange-oversupply term is a placeholder.

## 3. Elasticity — how our own output presses the price

Selling `q` units/h raises saturation, and `m = 1 - S/2`, so **every unit we add lowers the price we
(and everyone) realize**. We want the largest add-rate that keeps the price within a tolerance band.

### 3.1 Structural elasticity (always available, from the verified curve)

Accept at most a fractional price drop `τ` (default **0.12**). Require `m_after ≥ (1-τ)·m_now`:

```
1 - S_after/2 ≥ (1-τ)(1 - S_now/2)
⇒  ΔS_max = τ · (2 - S_now)                          # elegant: tolerance × distance-to-dead
```

Map saturation back to a flow using the sink `A`. Adding a sustained flow equal to the full
absorption raises saturation by `β` (default **β = 1.0**), so the price-stable add-rate is:

```
headroomSat  = max( 0, τ·(2 - S_now) - k_t·dS )      # k_t ≈ 5, dS in /day: draining ADDS room
headroomFlow = headroomSat · A / β                    # units/h we can add within the τ band
```

The `-k_t·dS` term is the trend credit/penalty: a draining lake (dS<0) hands back headroom, a
flooding lake (dS>0) removes it.

### 3.2 Empirical elasticity (when we have our own sell data)

`knowledge.json.sellRates[k]` records `qty/hours` the game projects at a chosen `lastPrice` — it
already bakes in store level, weather (`weather.sellingSpeedMultiplier`, currently 0.699) and
saturation. Two rows at different prices give a local slope `dRate/dPrice` = direct elasticity; use it
in place of `β` when `samples ≥ 2` and both are `fresh`.

> **Do not trust a single sellRate as the sustainable rate.** Apples show `sellRate=524/h` at $5.05 —
> that is the *burst* rate emptying our inventory into stores; it will saturate and collapse to the
> `unitsSoldAnHour=110/h` realm sink. The burst figure is the retail-level mirror of the paper-$/h
> mirage. Sustainable ≈ `min(unitsSoldAnHour, headroomFlow)`, never the burst projection.

## 4. The discount formula

```
g = producedPerHourRaw · 0.8087                       # level-1 output/h (as in industry-report.js)

── RETAIL / RESTAURANT branch (retail entry exists) ─────────────────────────
if avgPrice is null or 0 and not restaurant-only:     realizableRate = 0        # DEAD-LAKE
A            = unitsSoldAnHour + amountSoldRestaurant/24
headroomSat  = max(0, τ·(2 - S) - k_t·dS)
headroomFlow = headroomSat · A / β                    # elasticity-limited add-rate
realizableRate = min( g, headroomFlow )               # can't sell faster than we make, nor than the band allows

── EXCHANGE / B2B branch (no retail entry) ──────────────────────────────────
A = derivedDemand(k)                                  # realized-seeded recursion, §1.4
if A < A_min and A < max(5, 0.5·g):  realizableRate = 0                         # MIRAGE gate
else:  realizableRate = min( g, α·A ) · priceKeepExch(k)     # α = max share one operator claims
```

Then feed downstream exactly as today, swapping `rate → realizableRate`:

```
realizable$/h = (netSell - inputCost) · realizableRate - wage
```

`realizableFraction = realizableRate / g` ∈ [0,1] is the headline "how much of the paper is real"
number for the board. Constants (§7): `τ=0.12, β=1.0, k_t=5, α=0.34, A_min=50, DoS_dead=30, p_band=0.05`.

## 7. Constants (tunable — start here)

| symbol   | default | role                                                            |
|----------|---------|-----------------------------------------------------------------|
| `τ`      | 0.12    | tolerated price drop from our own adds (elasticity band)        |
| `β`      | 1.0     | saturation gained per unit of `A`-sized added flow              |
| `k_t`    | 5       | trend weight (draining lake → more headroom)                    |
| `α`      | 0.34    | max share of realm derived demand one operator claims (B2B)     |
| `A_min`  | 50 u/h  | viability floor for B2B derived demand (MIRAGE gate)            |
| `DoS_dead`| 30 d   | sell-book days-of-supply at which `priceKeepExch → 0`           |
| `p_band` | 0.05    | price window for counting sell-book depth                       |

Recalibrate `β`/`τ` against `knowledge.json.sellRates` once ≥2 fresh price points exist per product;
the structural curve is the prior, our own sell data is the likelihood.

## 8. `realizable.js` skeleton

```
load game-facts.resources, board-data.market (retail+ticker+orderBooks), knowledge.sellRates
build consumers graph from recipe; solve realized-seeded fixed point → A_der[k]   (§1.4)
for each producible kind k:
    g = rate*0.8087
    if retail entry:
        if avgPrice falsy and restaurant==0: emit {rr:0, flag:'DEAD-LAKE'}; continue
        A = unitsSoldAnHour + restaurant/24
        dS = slope(retailData.saturation, last 7)          # or snapshots if stale
        head = max(0, τ*(2-S) - k_t*dS) * A / β
        rr = min(g, head); flag = OPEN|DRAINING|OVERSUPPLIED
    else:                                                   # B2B
        A = A_der[k]
        if A < A_min and A < max(5,0.5*g): emit {rr:0, flag:'MIRAGE'}; continue
        rr = min(g, α*A) * priceKeepExch(k, bookStale)
    emit { realizableRate: rr, realizableFraction: rr/g, absorption:A, flag }
rank by (netSell-inputCost)*realizableRate - wage        # replaces industry-report paper $/h
```
