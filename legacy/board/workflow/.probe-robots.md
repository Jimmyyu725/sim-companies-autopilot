# Probe: INSTALL ROBOTS dialog (2026-07-24)

Probed READ-ONLY via `probe-robots.js` on Mill 55042846 (size 1) and Farm 54959369 (size 3),
both busy at probe time. Dialog opened, read, closed with "I changed my mind" — nothing
committed, nothing bought. Screenshot: `shots/robots-probe.png`. Bundle facts cross-checked
against `bundle-main.js`; `game-facts.json` has NO robots fields at all.

## What robots actually do (correcting the task's assumption)

- **There is NO production bonus.** The "Production increase by {percent}%" string in the
  bundle (`Building.productionIncrease`, percent = 100/size) belongs to the **UPGRADE**
  dialog, not robots.
- Robots give a **3% wage cost reduction** (hardcoded: dialog renders `percent: 3` /
  `savingsPercent: 3`; profit calcs apply `robotsSpecialization ? 0.97 : 1` to the
  building's wage term).
- Cost of the deal:
  - Building is **locked to ONE product** (`robotsSpecialization` = resource dbLetter).
  - **Cannot upgrade or downgrade** while robots installed.
  - Install downtime = `size × buildDuration` seconds (Mill L1: 3:00h; Farm L3: 3×1h = 3:00h).
    Rushable with SimBoost "Robots Installation Speedup".
  - Uninstall anytime (building must be idle) → refunds only **50% of robots at Q0**.

## Measured dialog numbers

| Building | Size | Robots needed | Quality | Exchange price | Total cost |
|---|---|---|---|---|---|
| Mill 55042846 | 1 | x17 Q0+ | Q0+ | 17 @ $630 | $10,710 |
| Farm 54959369 | 3 | x3 Q0+ | Q0+ | 3 @ $625 | $1,875 |

## Per-level formulas (from bundle, validated by both probes)

```
AVERAGE_SALARY = 345, ROBOT_COST = 940, maxQ = 12   (bundle constants)
e         = salaryModifier * (345*24*7*5*0.03) / 940   // = salaryModifier * 9.24894
perLevel  = max(1, ceil(e + (e - 4.5) * 1.2))          // robots per building level
needed    = perLevel * size
qualityNeeded = min(floor(size / 4), 12)               // L1-3 -> Q0+, L4-7 -> Q1+, ...
```

- Mill salaryModifier = 1.1 → e = 10.174 → perLevel 17 → 17×1 = **17** (matches).
- Farm salaryModifier = 0.3 → e = 2.775 → perLevel 1 → 1×3 = **3** (matches).
- Sourcing: warehouse robots (quality ≥ needed, non-blocked) are used first; the dialog
  quotes the cheapest exchange sell orders for the remainder. Blocked robots in WH show a
  warning and disable Buy missing.

## Economics quick take

Mill L1: $10,710 + 3h downtime buys 3% of a $380/h wage ≈ $11.4/h → **~39 days payback**,
plus the upgrade lock. Farm L3: $1,875 saves 3% of 3×$104/h ≈ $9.4/h → **~8 days payback**.
Low-wage buildings (Farm, Plantation) are far better robot targets because of the
`max(1, …)` floor and cheap Q0 robots ($625-630 vs the formula's $940 assumption).

## Exact DOM structure (for a future pages/robots-install.js primitive)

1. **Opener** (on /b/<id>/, only when building owned & production category & no robots yet):
   `button.btn-secondary` containing `img[alt="Install robots"]`, innerText "Install robots".
   If robots are installed the same slot shows "Uninstall robots" instead.
   Opening is state-only (React `robotsConfirmation`) — safe to click.
2. **Modal**: matches `[class*=odal]` filtered by /Install robots/ header text (same trick
   as strat-upgrade-cost.js). The page opener STAYS in the DOM while the modal is open
   (same trap as scrap.js — exclude it by identity when hunting the confirm).
3. **Requirements block** text shape:
   `x<N> Robots Q<q>+ <fromWH> <fromExchange> @ $<unit> Exchange purchase cost $<X>
    Sourcing cost of warehouse resources $<Y> $<total>`.
4. **Specialization tiles**: styled `div`s (emotion class, css target `emrfv320`), each =
   `img` + `span` with the resource name, under an h4 "SELECT SPECIALIZATION". onClick is a
   plain React prop so `.click()` should register; if not, fall back to real-mouse clicks
   (sell-exchange-ui.js pattern). Selected tile gets background `rgba(137,178,208,0.9)`.
   Until one is selected the dialog shows "Please select specialization resource".
5. **Footer — renders ONLY when the building is idle** (`!isBusy`); when busy it is replaced
   by bold "Building is currently busy and cannot be upgraded" and NO commit is possible
   (what both probes saw):
   - `button.btn-secondary` **"Buy missing"** — SPENDS MONEY (buys robots from exchange).
     Disabled unless robots are actually missing. NEVER click while probing.
   - `button.btn-primary` **"Install robots"** — the FINAL commit. Disabled until enough
     robots are in the warehouse AND a specialization is selected. Fires
     `PATCH /api/v2/companies/me/buildings/<id>/ {robots:"<dbLetter>"}` through the app
     (direct API replay is blocked by X-Ts/X-Prot bot-protection; must go through UI).
   - Uninstall flow is the same endpoint with `{robots:null}`.
6. **Cancel**: `button.link-button` "I changed my mind" (works, verified twice) or the
   `button.close` X. Both close cleanly; `dialogGone` verified after click.
7. `GET /api/v2/companies/me/buildings/<id>/` returns **405** — the endpoint is PATCH-only.
   Read robots state from the buildings list payload (`robotsSpecialization` field, null
   when none) that the tick already captures.

## Primitive gating requirements (when we build it)

- Self-gate on `confirm:true`; dry run = open, parse the table above, click
  "I changed my mind", return numbers.
- Refuse if the building is busy (footer absent) or if the primary button set is ambiguous;

  before the install itself.
- Verify after commit: building payload's `robotsSpecialization` equals the requested
  dbLetter (installation shows "Installing robots" busy state for size×buildDuration).
