# Exchange VOLUME tracker — probe findings + recommended design

Scout run 2026-07-25 ~01:00 UTC. Probes: `vol-probe.js`, `vol-probe2.js`, `vol-probe3.js`
(all pure in-page fetches via `cdp.evaluate`, no lock, all ended with `cdp.close()`).

## 1. Probe findings

### 1a. `resources-transactions` — NOT usable as a global trade feed

| Path | Result |
|---|---|
| `/api/v2/resources-transactions/` | 404 (HTML) |
| `/api/v2/resources-transactions/0/` | 404 |
| `/api/v2/resources-transactions/<kind>/` | 404 |
| `/api/v2/resources-transactions/0/<kind>/` | **200, always `[]`** |
| `/api/v3/resources-transactions/...` (any shape) | 404 |

The only live shape is `/api/v2/resources-transactions/0/<kind>/` (realm/kind) and it returned
an empty array for EVERY kind probed — including 119 (coffee powder, we sold hours earlier) and
102 (bricks, we bought hours earlier). So it is not a global feed, and it is not even a working
own-company feed for recent trades; `?limit=` / `?page=` change nothing. Dead end — do not build
on it.

Also checked, also dead ends:
- Ticker `/api/v3/market-ticker/0/` rows carry only `{kind, image, price, is_up, realmId}` —
  no volume field.
- Graph-endpoint guesses (`resources-hour-data`, `market-graph`, v1/v2/v3) all 404.

### 1b. Order book `/api/v3/market/0/<kind>/` — has per-order ids. This is the source.

Each row is a standing sell order, price-ascending. Field list (verified on kinds 1, 5, 102):

`id, kind, quantity, quality, price, datetimeDecayUpdated, seller{id, company, realmId, logo,
certificates, contest_wins, npc, courseId, ip}, posted, fees`

Sample row (kind 1, power):

```json

  "datetimeDecayUpdated": "2026-07-25T00:57:09.874596+00:00",
```

Depth cap: power returned exactly **200 rows** (grapes 91, bricks <200) — the endpoint caps at
200. The cap matters for the diff (see 2c).

## 2. Recommended design: order-level diff

### 2a. Volume math (per kind, per interval)

Keep the previous snapshot as `id -> {q, p}`. On each new snapshot:

- **Persisting id, quantity dropped**: add `prev.q - curr.q` units (partial fill). Ignore
  increases (shouldn't happen).
- **Vanished id**: add `prev.q` units (fully bought) — EXCEPT the cap-ambiguity case in 2c.
- **New id**: ignore (new listing, not a purchase). This is exactly what makes naive
  inventory-diff wrong and this method right.
- Dollar volume: same sums weighted by the order's `prev.p`.

Known inflation: cancels and decay-expiries also remove orders, so measured volume slightly
overstates true purchases. Acceptable; optionally tag vanished orders priced >10% above the
best ask as "suspected cancel" in a separate bucket, since nobody market-buys deep into the book.

### 2b. Failure tolerance for free

Only overwrite a kind's saved snapshot after a successful fetch of that kind. If a run (or one
kind) fails, the next successful diff simply spans a longer window — cumulative volume is
preserved, just binned coarser. So a collision with a navigating strategist/board session costs
resolution, never correctness.

### 2c. The 200-row cap guard

If the PREVIOUS book was full (200 rows) and a vanished order's price >= the highest price
visible in the CURRENT book while the current book is also full, the order may merely have been
displaced past rank 200 by cheaper new listings — not bought. Count those units into a separate
`amb` (ambiguous) bucket instead of volume. If the current book is not full, nothing can be
hidden and every vanish is real.

### 2d. Fetch mechanics + cadence for all 142 kinds

- ONE `cdp.evaluate` body-string per run: chunked `Promise.all` of `api('/api/v3/market/0/<k>/')`,
  chunk size 12, ~200 ms between chunks -> ~10-14 s total, safely under cdp.js's 60 s message
  timeout. Return compact `{kind: [[id,q,p],...]}` (~1-2 MB, fine for returnByValue).
- Pure in-page fetch, no navigation -> **NO `.tick.lock`** (LESSONS B2/B6 govern navigating
  reads only). Wrap the cron in `timeout 90` regardless.
- Script MUST end `cdp.close(); process.exit(0);` (and close+exit(1) in catch).
- **Cron: `2-58/4`** — every 4 min on EVEN minutes only. Verified against the live crontab:
  the only browser cron is the price collector on ODD minutes (`1-59/2`, navigates + holds the
  lock ~15 s); brain gate (odd minutes) and build-facts-db (08:20 daily) are non-CDP. A plain
  `*/5` is impossible here: 5-min steps alternate parity and would land on odd minutes. `2-58/4`
  never shares a minute with any browser cron and beats the 5-min target.

Load: 15 runs/h x 142 GETs = ~2100 in-page GETs/h, same order as what board-data.js bursts do;
spread in 12-wide chunks this is gentle. If it ever trips Cloudflare, fall back to 10-min cadence
(`4-54/10`, still all-even) before anything fancier.

### 2e. Storage

Under `price-tracker/data/`:

- **`volume.jsonl`** (append, one line per successful run):
  `{"t0":<prev unix>,"t1":<curr unix>,"u":{"<kind>":units,...},"v":{"<kind>":dollars,...},"amb":{"<kind>":units,...},"kinds":142,"fail":[<kinds that errored>]}`
  Zero-volume kinds omitted -> lines stay small. Trim to last 20000 lines like collect.js
  (~55 days at 4-min cadence).
- **`book-state.json`** (overwritten via tmp-file + rename): per kind
  `{"full":bool,"top":price,"last":price,"o":{"<id>":[q,p],...}}` plus a run timestamp.
  ~142 kinds x <=200 orders -> ~2-3 MB, bounded by the cap.

### 2f. Deployment order (LESSONS A4)

1. Write `price-tracker/volume.js`; run once by hand -> seeds book-state.json, logs "seeded".
2. Run again by hand ~5 min later -> verify a sane volume.jsonl line (power should show volume
   almost every interval; dead kinds zero).
3. Only then add the cron line (with `cd /srv/appdata/chrome-automation/sim &&`, printf-built,
   grep-verified per LESSONS B7). Watch one full hour of collect.log-style output before
   trusting it.

## 3. Verdict

- Source: **order-level diff of `/api/v3/market/0/<kind>/`** (has stable per-order `id`).
- `resources-transactions`: exists only as `/api/v2/.../0/<kind>/`, returns 200 + empty even for
  our own fresh trades — abandoned.
- Cadence: every 4 min, even minutes (`2-58/4`), one batched in-page evaluate, no lock.
- Caveats baked in: new-listing masking solved by id-diff; 200-row cap handled by the `amb`
  bucket; cancels/expiries slightly inflate volume (documented, optionally bucketed).

## 4. POST-IMPLEMENTATION ADDENDUM (2026-07-25, implementer session)

Section 2d's fetch plan (all 142 kinds per run, 12-wide chunks) is NOT viable — implemented
as designed, the very first run got 429s after ~14 requests. Measured behaviour of
`/api/v3/market/0/<kind>/` (probe after a 120 s cooldown, sequential no-delay requests):
exactly **10 × 200 then 429**, no Retry-After header. ~1 min after a 429 storm only ~1 request
succeeded, while ~80 s of QUIET yielded the full 10 — i.e. a ~10-token bucket refilling in
about a minute, and hammering into 429s appears to penalize/reset the refill.

Implemented adaptation (everything else — order-diff math, amb bucket, per-kind
failure-tolerance, storage shapes, no lock — is as designed):

- **Rotating cohort**: each run fetches 10 kinds (serial, 500 ms apart, STOP at first 429),
  cursor persisted in `book-state.json`; full sweep of 142 kinds every ~30 min.
- **Cron `2-58/2`** (even minutes, all free of browser crons) instead of `2-58/4`.
- `book-state.json` snapshots carry a per-kind `t`; volume.jsonl `t0` = oldest prev-snapshot
  time among the kinds diffed in that line (per-kind bins are ~30 min, not 4 min).
- Consequence for consumers: per-kind volume is binned at sweep cadence (~30 min), so UI
  windows shorter than ~30 min only see the cohorts that happened to run inside the window.
